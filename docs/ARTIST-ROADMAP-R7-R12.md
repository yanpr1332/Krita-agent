# Krita Agent 通用 AI 画师开发路线图（Round 7–12）

> **状态：已讨论并记录的未来开发方案（PROPOSED），不是已实现功能或已通过的验收。**
>
> 记录日期：2026-11-10。基线：`feat/round6-brush-dynamics`，Round 6 最新记录 `8f84eea`。
>
> 本文件是 Round 7–12 的长期开发目标和验收方向。每轮启动前可细化任务，但不得未经记录而放弃本文件的三项核心目标。与已有 `docs/ARTWORK-ACCEPTANCE.md`、`AGENTS.md` 冲突时，以更严格的真实作品/安全验收要求为准。

## 1. 产品目标与非目标

### 1.1 三项不可丢失的目标

1. **真实绘画、像人一样思考和落笔。** Agent 要观察画面、理解结构、选择技法、分阶段作画、检查并修改。笔触的方向、密度、长度、颜色、压感、边缘、纹理应由物体、光照、空间关系和绘画意图共同决定。不能以随机噪声或堆砌笔触数量伪装自然性。
2. **常见题材的通用能力。** 不能只会画山水落日。应覆盖风景、静物、建筑/室内、人物、动物、插画/漫画等，并对未见过的题目与物体组合泛化。画风、题材、对象和材质是不同维度，不应靠一个固定的自然风景类别列表驱动全部绘画。
3. **临摹参考图并积累绘画技法。** 接受有权使用的参考图，分析构图、比例、光影、色彩、材质、笔法和风格，以 Krita 原生可编辑绘制过程重新创作；能够把分析出的可复用方法保存为带来源的风格/技法档案。**这种学习不等于自动修改大模型权重**，模型训练/微调需要单独数据、许可、成本和验收计划。

### 1.2 预期产品定位

目标是**多题材、分阶段、有视觉反馈、可人工指导的通用 Krita AI 绘画助手/半自主画师**。不是把参考图片粘贴到 KRA 后宣称临摹成功；不是只输出 PNG 的图像生成器；不是通过人为脚本匹配固定考题；也不宣称无需人工审美判断即可稳定达到专业画师水平。

优先保留：真实 Krita 原生笔刷、可编辑图层、可追溯的每阶段笔触和计划、失败版本及证据。允许将来加入用户批准的辅助视觉分析，但不得以外部位图取代原生绘画验收。

## 2. 当前基线与待解决缺口

### 已有工程能力（只引用有证据的范围）

- Round 1–4：经文档记录的本机 Bridge、图层、蒙版、快照、任务调度、压感/笔刷档案及 ScenePlan v2 基础。
- Round 5：基于可选 HTTPS JSON 模型提供者的 ScenePlan v3、独立视觉评审/ROI 修订接口、版本归档、KRA 重新打开完整性门禁；模型接入源码存在，并非每次本地验收都使用真实模型 API。
- Round 6：逐笔切换预设/颜色/大小/透明度、命名风格、弧长压感曲线、更多绘画元素、局部多风格修订；Stable / Next Qt5 / Next Qt6 原生笔刷验证与修复已写入 `ROUND6-REACCEPTANCE.md`。完整作品的**独立人工验收和正式审计仍待完成**。
- Round 6 记录的两次不同绘画计划：889 笔对比 1,969 笔；粗略重复轨迹签名从 94 增至 646。该数字不是画质评分，且性能对比不是控制变量实验，但提醒必须解决几何重复，而非只继续加笔。

### 关键瓶颈

1. 当前 `scene_v3.py` 的对象类别和 `strategies_v3.py` 的固定尺寸/压力策略高度偏向自然风景；`object/custom` 不足以表达人物解剖、面部结构、透视物体、织物、毛发等。
2. 一次性让语言模型输出数百至数千条绝对坐标笔触，难以保持结构一致性，也不利于按阶段观察和修订。
3. 即使逐笔参数有变化，云、水、林木、雪线等仍可能采用类似几何笔法，呈现机械重复。
4. 单一锁定的 Needle Lake 风景基准无法证明多题材泛化。
5. KRA fresh-reopen 少量 RGB 像素漂移的根因尚未解决；修复层是独立保全版本，不是根因修复。
6. 当前 API 视觉评审的源码能力不等于稳定、经济且可信的自动艺术验收；人类独立评审仍是最终交付门禁。

## 3. 总体架构原则

### 3.1 把“绘画决策”与“原生笔触执行”分开

建议逐步引入以下可审查中间表示（具体类名在实施轮次中确定）：

1. **ArtBrief / ReferenceAnalysis：** 用户目的、题材、画风、构图要求、合法参考图、要保留/避免的视觉特征。
2. **CompositionPlan：** 主体与部件的层次关系、姿态/透视/比例、遮挡关系、光源、负空间、主色调、焦点。
3. **StagePlan：** 草图与大形 → 明度与色块 → 体积塑造 → 材质 → 局部细节 → 全局校正；每阶段可暂停、预览、接受或修订。
4. **PaintIntent / MaterialRecipe：** 对每个区域描述“为什么要画这一组笔触”，例如沿表面法线塑形、表现毛发生长方向、在光源处做边缘高光；写明目标区域、笔刷类别、尺度、方向场、密度、色彩约束、随机种子、质量预算。
5. **Safe Stroke Compiler：** 由可验证的几何/材质程序把意图扩展成有限、确定、受边界约束的原生笔触；复用现有 ScenePlan、Bridge、审计和 KRA 版本机制。
6. **Visual Feedback：** 对真实 Krita 阶段预览/PNG 做区域级质量判断，提出有限修订而非自动无限循环；保留前后对照、hash、失败样例与人工决定。

大模型优先决定 **画什么、先后顺序、色彩结构、哪里不对、如何改**；程序负责精确、安全、可复现地绘制笔触。不能强迫模型一次性亲自计算全部底层点坐标，也不能让程序用固定风景脚本代替创作决策。

### 3.2 三套相互独立的知识体系

- **Subjects（题材/结构）：** 人体、脸、动物、植物、车辆、建筑、容器等的部件、比例、关节、透视、遮挡与语义关系。
- **Materials（材质/笔法）：** 皮肤、头发、毛皮、金属、玻璃、布料、木材、石头、雪、水、云、叶片等的边缘、纹理、反射、方向场和压感策略。
- **Styles（风格/表现）：** 水彩、油画感、铅笔速写、漫画、平涂插画、厚涂等的色彩/层次/笔刷组合与绘画顺序。

不能把“山”直接等同于“texture 笔刷”，或把“人物”固定为单一绘制样式。同一物体可能有多种材质和风格。

### 3.3 始终保留安全与证据边界

- 任何模型输出都是不可信的结构化候选：必须通过字段、坐标、配额、路径和原生命令白名单校验；不可直接生成代码、插件或任意 IPC。
- 原生执行和局部修订保持显式确认与版本保全；不对结果未知的 Krita 操作自动重放。
- 每次重要绘画保留原生 KRA、PNG、Krita 屏幕截图、三阶段预览、图层真实贡献、原始计划、参数、日志、失败版本和双重审查证据。
- 重新打开 KRA 的严格一致性仍是独立门禁；微小差异可作为诊断展示，但不自动算通过。修复必须另存版本并保留失败原件。
- 参考图与风格库保留来源、许可、用户授权和公开发布限制。避免未经许可的大规模抓取或发布临摹素材。
- 不将笔触数、图层数、预设种类数、重复签名分数或视觉模型的一句“pass”当作完整作品通过的替代品。

## 4. 分轮开发计划总览

| 轮次 | 首要能力 | 与前序依赖 | 最低可验证交付 |
| --- | --- | --- | --- |
| **R7** | 通用多阶段场景架构 | 基于 R6 安全编译器 | 新的分层规划表示、旧计划兼容适配、真实多阶段作品证据 |
| **R8** | 自然笔触与材质绘制 | R7 区域/笔触意图 | 多材质原生笔法库、抗重复诊断、可见的材质差异 |
| **R9** | 多题材结构与绘画策略 | R7/R8 | 人物/动物/静物/建筑/插画等未知题目的实例与失败分析 |
| **R10** | 参考图临摹与技法学习 | R7–R9 | 参考解析、原生临摹、可追溯风格/技法档案 |
| **R11** | API 视觉评审与有界自主修订 | R10 和已有 R5 接口 | 真实多模态 API 验收回路、逐轮修改证据、人工复核 |
| **R12** | 通用能力整合与正式验收 | R7–R11 | 跨题材隐藏测试、可靠交付、性能与质量报告 |

这是**六轮核心大开发的估算**，不是预先宣称六轮一定足够。每轮以能力和验收门禁结束，必要时安排 1–2 轮专项修复/优化。一个 Round 应是有多个彼此关联模块的大开发批次，而非一次小补丁。

## 5. Round 7 — 通用多阶段绘画架构

### 目标

摆脱“固定风景对象类型 + 一次性生成千笔”的结构；形成能够支持任意题材的、分阶段可观察的绘画规划框架。

### 主要开发包

- **R7-A / Schema：** 设计版本化的层级主体/部件/材质/区域表示；支持自定义语义标签、父子关系、坐标系、区域掩膜/轮廓、遮挡、景深、光照和透视约束。保留 ScenePlan v3 的显式兼容适配，不能静默破坏 R5/R6 任务。
- **R7-B / Stages：** 独立的草图、构图、大色块、结构塑形、细节、最终统一阶段；有阶段任务预算、检查点和预览，并能只重做某个局部或阶段。
- **R7-C / Intent Compiler：** 增加“目的导向绘画指令”，将模型提出的区域目标翻译成有限的原生笔触序列；所有派生几何必须可验证、种子可复现、可审阅。
- **R7-D / Planner：** 模型分级输出构图/结构、阶段任务和笔触意图，不再依赖一次吐出几千条点坐标；允许用户锁定主体位置或画风。
- **R7-E / Integration：** CLI、SDK、报告格式、文档、失败恢复和离线/原生回归统一接入。

### 验收要点

- 现有 Round 6 场景依然可编译并通过安全回归。
- 至少对风景、单一静物、简单角色三个不同主题展示完整分阶段流程，不能为每题写专属固定画法。
- 中途停止、恢复、阶段修订、真实图层贡献和严格 KRA 重新打开均有证据。
- 报告模型输出 token/计划规模/原生笔触数量，证明上层规划不需要传送所有底层笔触坐标。
- 人工实际观察中间稿与最终稿；未经人工审核不得宣布“绘画能力完成”。

## 6. Round 8 — 自然笔触、材质与反机械化

### 目标

让每一笔有结构和视觉目的；使真实作品的云、水、石、植被、织物等表现出不同的笔触机制，而非大量类似线条。

### 主要开发包

- **R8-A / Gesture Fields：** 根据轮廓、曲面方向、透视、光线与局部目标形成笔触方向场；支持长度、宽度、弯曲、边缘、角度、间距、疏密、压感与颜色的协同变化。
- **R8-B / Material Recipes：** 建立可扩展的材质笔法库；首批至少覆盖云、水、岩石/雪、树叶/草、皮肤/毛发、金属/玻璃/布料中若干差异显著的类别，并允许同一材质跨画风表达。
- **R8-C / Color and Layering：** 明暗块→半透明叠色→局部色彩温度→细节；严格区分 Krita 原生叠加和简单 RGB 计算，不伪称未验证的混色模型。
- **R8-D / Anti-repetition：** 检测轨迹重复、规则间距、重复树形/云形、空白区域与不合理均匀密度；诊断必须结合构图意图，不能以盲目随机抖动刷指标。
- **R8-E / Native Evidence：** 跨多个真实 Krita 预设和构建验证压力、纹理、透明度、连续性以及可编辑层结果。

### 验收要点

- 同一构图锁定，比较旧笔法与新笔法，并进行独立人工盲评。
- 对云、水、岩石、植被等具体区域分别解释画面有何改善；展示实际 PNG 裁切和原生笔刷证据。
- 记录重复轨迹比例、有效覆盖、时间、笔刷类别与主观画质，但任何单一计数不能代替视觉判断。
- 不通过把像素参考图直接贴进画布来取得更好的观感。

## 7. Round 9 — 常见题材的泛化

### 目标

从风景扩展到人物、动物、静物、建筑/室内、交通/机械和漫画/幻想插画；结构合理性和物体可识别性优先于装饰性细节。

### 主要开发包

- **R9-A / Structure：** 人体与面部关键部件、动作、动物体态、物体轮廓和透视约束；让主体能够被拆解为可绘画的结构，不依赖几十个特例。
- **R9-B / Occlusion and Composition：** 物体重叠、遮挡、体积、比例、负空间、光源和景别；支持局部约束与用户锁定。
- **R9-C / Subject Strategies：** 按主体、材质、风格组合技术，而非只按固定 `kind` 查一个笔刷尺寸或压感。
- **R9-D / Failure Recovery：** 让评审能够指出“手部结构不对”“透视消失点冲突”“动物腿部数量不对”等语义问题，并回到对应结构阶段修改。

### 验收要点

建立事前封存的跨题材题库，至少六组题材，每组不少于三幅此前未用于开发调参的题目。每组必须有真实可编辑 KRA/PNG、阶段截图、独立人工结果与失败案例。不得为验收画面单独硬编码脚本。复杂五官、手部、多人场景应明确标注难度，不因缺陷而偷偷剔除样本。

## 8. Round 10 — 参考图临摹与可复用技法学习

### 两种不同能力

1. **Reference Repainting（临摹）：** 在用户授权的参考图上分析主题、构图、比例、明暗、色彩、边缘与笔触；输出可审查分阶段绘画计划，在 Krita 中重新绘制可编辑作品。视觉相似可作为评估维度，但不能以“导入并贴图”取代真实绘制。
2. **Style/Technique Learning（技法学习）：** 从多张已获许可的作品提取通用配色、材料处理、笔刷配置、布局和流程，存成有来源、版本和适用条件的技法档案。这里是知识提取与检索复用，不是自动微调模型参数。

### 主要开发包

- **R10-A / Analysis：** 参考图区域和主体解析、色彩比例、结构和光照关系、构图布局、笔触方向与材质的可信度记录。
- **R10-B / Repaint Modes：** 区分结构临摹、风格参考、自由改编模式；让用户明确是否强调构图一致、色调一致或笔法一致。
- **R10-C / Technique Library：** 记录笔刷预设及适用构建、参数、压力响应、例图、来源/许可、失败条件；不能把未经验证的猜测标为经验事实。
- **R10-D / Multi-reference：** 允许分别从不同合法参考中提取构图、色彩或材质，但清楚标记来源与冲突。
- **R10-E / Comparison：** 参考图与实际 Krita 绘画的区域/颜色/结构比较及人工审核。

### 验收要点

在不参与调参的合法参考图上分别测试结构临摹、风格借鉴和多参考组合；证明成品来自原生画笔/层，保留 KRA 源文件和步骤追溯。不承诺对任意大师作品做到像素级复刻。

## 9. Round 11 — 多模态 API 验收与有界视觉闭环

### API 时机的明确决定

**完整的付费/云端大模型艺术自动验收可以推迟到 Round 11。** R7–R10 用本地可复现测试、人工观察和模拟/可选模型调用推进，不以缺少 API Key 阻塞核心绘画引擎。

但是：R7 之后的语义规划、R10 的参考图分析本身可能需要具备视觉能力的模型；“延后自动验收 API”不等于禁止提前使用用户明确配置的模型协助创作。现有 `ChatJSONProvider`、视觉评审和 ROI 修订接口应复用，不能重新发明不安全的任意命令通道。

### 主要开发包

- **R11-A / Provider：** 可插拔模型接口，显式授权、HTTPS、环境变量密钥、调用成本/超时/失败状态记录；允许不调用 API 的离线模式。
- **R11-B / Critic：** 将真实参考图（若有）、真实完整 PNG、区域裁切、阶段预览、图层贡献和目标约束一起交给模型；要求针对可见像素给出具体观察，而非根据文件名和对象标签猜测。
- **R11-C / Revision Loop：** 问题定位→生成候选→安全校验→显式批准→新可编辑图层局部修改→重新导出与评审；限制迭代次数、预算和地域，保留所有失败版本；不做无限自我强化循环。
- **R11-D / Independent Judgement：** 模型参与的创作/修订和独立验收必须逻辑分离，人工审核身份不得由模型冒充。比较改动前后是否真正改善。
- **R11-E / Benchmarking：** 测量 API 调用次数、时间、费用、成功/失败、幻觉/误判案例，并为“评审认为通过但人工否决”保留证据。

### 验收要点

先使用模拟提供者和离线固定图做安全回归；再在用户授权及已配置密钥时进行真实 API 试验。至少涵盖修订有效、修订无效、误判、超预算、超时、KRA 重开不一致、人工拒绝等情形。模型 `pass` 不等于正式作品通过。

## 10. Round 12 — 全面整合、性能与作品级验收

### 主要开发包

- **R12-A / Performance：** 测量规划、编译、逐笔执行、保存、重新打开、评审、局部修订的分段耗时；优化重复配置、内存、批处理、画布尺寸和资源分配，保留安全中断/恢复。
- **R12-B / Reliability：** 调查 KRA 重新打开微小像素漂移及色彩配置；根因不明时维持严格失败与独立修复版保全。跨 Stable/Next 已有真实构建做回归，不把某构建结果推广到全部版本。
- **R12-C / User Experience：** 用户选择画风、参考图、主体、局部修订区域、复杂度/耗时预算；可查看阶段进度、实际预览与失败原因。
- **R12-D / Whole-art Benchmark：** 多题材、未见过的文本题目与参考图；真正的可编辑 KRA、完整PNG、独立视觉审核和人工评价；公布失败率、素材来源、成本、时长和可复现步骤。
- **R12-E / Delivery：** 文档、示例、能力矩阵、已知限制、版本兼容表、发布前隐私/版权检查与选定的公开验收证据。

### 验收协议（建议起点，阈值在前期试验后固定）

- 事先封存至少 **6 题材 × 3 未见过文本任务 = 18 项**，再增加至少 **6 项合法参考图临摹/风格任务**，形成至少 24 项多样化测试。
- 各任务事先确定题材、复杂度、参考与限制；留存全部尝试，包括失败，不只挑选优秀成品。
- **Technical Gate：** 原生绘制、非空且有意义的可编辑图层、源与执行追溯、检查点、严格 Export Integrity 和 Reopen Stability。
- **Artwork Gate：** 构图与主体识别、结构/比例、材质与光影、笔触自然性、参考图遵循情况、画面完成度；独立视觉模型和真实人工评审分别记录。
- **Generalization Gate：** 不允许为测试题临时创建专用硬编码画法；题材之间可迁移的技能必须通过未见任务体现。
- **Performance Gate：** 记录全链路时间、真实原生命令数、模型调用和成本，并按相近复杂度比较；不以简单增加笔触数量作为进步。
- 每项分开给出 `source_implemented`、`offline_passed`、`native_verified`、`artwork_human_accepted`，绝不把一个状态自动升级为另一个。

## 11. 预期能力与现实限制

### 有把握追求的成果

- 高可靠性的 Krita 原生绘画控制，跨题材画出连贯的风格化插画或质量良好的草图；可编辑、可回溯和可局部修订。
- 支持自然语言任务、合法参考图、风格档案与材料技法组合。
- 具备阶段性观察和受约束的视觉反馈，在人工指导下进一步改善画面。
- 在若干适合的风格/题材中完成度较高；复杂问题能明确报告失败而非伪造通过。

### 不作保证的成果

- “任意图片都能精准复刻”、复杂多人物写实始终准确、稳定达到顶尖画师水平、完全零人工监督。
- 靠几轮程序开发就让基础大模型具备它原本没有的美术理解能力。
- 纯粹通过增加笔触数、引入压感随机量或单次 VLM 评分获得人类般的绘画判断。
- 所有 Krita 构建/全部笔刷/色彩深度下的相同行为，除非逐项实际验证。

成图上限取决于**视觉模型的理解与规划能力 × 绘画引擎的表达能力 × 视觉反馈质量**。其中任一项不足都会限制整体水平。

## 12. 阶段门禁与开发纪律

1. **先新建分支，再写任何文件。** 每一轮独立分支（例如 `feat/round7-generalist-scene` 至 `feat/round12-generalist-acceptance`）；跨轮次规划、未来路线图或验收政策调整也须独立 `docs/*` 分支。不得把 Round N+1 的方案或代码直接提交至 Round N 的现有分支；本规划保存在 `docs/round7-12-generalist-roadmap`，而非 Round 6。创建分支前先核实基准提交和开放 PR，创建后核实 ref，再开始写入。未明确目标时先询问；绝不默认合并 `main`。
2. 每轮包含多模块开发、离线测试、真实 Krita 测试、艺术作品证据及一份明确区分通过/未通过的验收报告。无法执行真实本机验证时必须标为 pending，并提供交接说明。
3. 对 Round 6 的画面进步要求：未来不把“一幅风景画”“更多图层”“更多 pass”“更高压感参数多样性”视为通用画师成功；必须有**不同题材**和**自然绘画的独立人类评价**。
4. 不接受通过修改固定基准、挑选幸存样本、粘贴参考图或伪造人工意见来提高通过率。
5. 任何计划变更应在该路线图的“变更记录”里注明动机和影响；不要无声删除用户三项长期目标或把 R11 API 验收提前变成 R7 的阻塞项。
6. 推进时优先更新核心架构，再扩展题材，再进行有意义的视觉反馈；避免重复构建已有 Controller、Bridge 和审计基础。
