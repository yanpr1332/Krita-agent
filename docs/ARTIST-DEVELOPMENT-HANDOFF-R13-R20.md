## 1. 下一步立即启动的工作（无需用户新增素材）

**R13 工作顺序：**

1. 对照 [Round 12 本地验收](ROUND12-LOCAL-ACCEPTANCE-REPORT.md) 记录最小可复现案例（Windows 归档反斜杠、Stable 多点透明笔触暗接缝、跨 Qt5/Qt6 运行差异、KRA 严格重开）。
2. 检查归档路径修复候选的代码/分支/PR 实际状态；如果只存在用户工作站的隔离提交，没有可访问远端 ref，不能假称已在 GitHub；必要时经用户授权再导入补丁或在新 R13 分支自行实现相同修复。
3. 保留原失败 fixtures，添加负面测试，修复 native endpoint 或 fallback 选项，先 T1 后最小 T2/T3。
4. 生成每构建能力矩阵和实际 Test Report；对 Stable 不支持的连续 API 要写“降级/不支持”而非硬造虚构接口。
5. 提交独立 R13 功能 PR，等待用户判断是否合并；不能直接改 main。

**R14 准备可与 R13 并行讨论但不可混到 R13 PR：**

1. 起草 ArtBrief/CompositionGraph/PaintPlan JSON schema、接口测试样本和迁移图。
2. 用 30 个独立新题，建立可重放的规划合同测试，参考 R12 的全部 invalid 原因，真实 API 测试前先用离线固定候选。
3. 确认允许的 ModelProvider 与费用/次数/上传权限，不依赖特定供应商、Key 或模型版本。
4. 必须保留 ScenePlan v2/v3/v4 兼容路径，不把重构变成不可逆大迁移。

## 2. 每轮实际交付清单（模板）

| 检查项 | 功能 PR 必须包含什么 |
| --- | --- |
| Scope | 功能包 A/B/C...、依赖、已知非目标，独立新分支 |
| API/Schema | 版本化接口、兼容旧 CLI、限制与错误字段 |
| Tests | Python 3.10 / 3.13 T1、故障/安全/边界/兼容；必要真实 T2/T3 |
| Documentation | 相关 API、设计约束、操作例子、失败与回退 |
| Native evidence | 真实 Krita 版本/Qt、editable KRA/PNG、stage、hash、严格 reopen |
| Artwork evidence | 同题材 A/B、真实 PNG/ROI、独立评审、失败案例 |
| Security/rights | 源图许可、显式外发、机密/本地数据 Git ignore、无任意 IPC |
| Status | 每项 PASS / FAIL / BLOCKED / NOT_RUN；不因 CI 绿就自称画质通过 |
| Review | PR 链接、当前 head SHA、未完成事项、人工是否需要操作 |

任务范围应尽量是一个完整的能力包，不要反复把一个微小调整包装成“大开发”。如果当轮功能需要用户持续视觉意见，在完成可检查的子门禁后再请求人审，而不是每个离线测试都让用户跑本地绘画。

## 3. 建议开发/验收分工

**云端 GitHub Agent：** 读真实仓库、提出接口/代码、在独立分支提交和测试、读 CI、记录失败、准备 PR、写迁移/验收说明；未经额外许可不通过 RDC 触碰本机。

**本地测试 Agent：** 在用户授权的隔离环境测试真实 Windows Krita，各版本独立会话；从真实 Krita 导出 KRA/PNG/阶段图，保存 ignored evidence；保留失败和原文件。只在用户明确允许时执行下载、安装、图片上传或收费调用；不能凭离线脚本合成图片冒充 native。

**用户/独立画质评审：** 提供审美目标/素材许可和关键反馈，审查小样实际图像；对完整作品进行独立人工签认，不由模型冒充。

**模型供应商：** 通过显式配置的 API 提供语义或视觉“建议”，不是代码执行器、系统文件管理员、永远正确的裁判或自动训练系统。

## 4. 素材何时需要、由用户怎样交付

建议以“首批 → 自动整理 → 抽查 → 扩量”的策略，避免把大量未经整理的线稿一次投入昂贵 API：

### 第 0 批（现在）

**不需要新图像。** R13–R14 使用 R12 已有原生失败案例、已锁定基准、之前保存的验证文件和合成测试。用户无需重复发送曾经配置在本地的 DeepSeek Key；实际使用前由本地 Agent 检查配置可用且执行权限明确。

### 第 1 批（R15–R16，建议）

- 5–10 张结构清楚、轮廓容易区分的线稿：杯子/植物/动物/人物/建筑最好各有代表。
- 5–10 张偏好的精细线条特写：可以从上一组挑选裁切，不必额外搜集。
- 2–3 个你常用、且允许测试的 Krita brush preset 名称或源文件。测试前先核实装在 Stable/Next 的资源差异。
- 每张给出简单标签“为什么喜欢/不喜欢”（自然收笔、线条节奏、毛发/褶皱方向、不规则但受控等）。

### 第 2 批（R17，建议）

- 5–10 张颜色和光照表现目标图，最好有同构图的线稿/彩稿对；
- 至少包含几种材质：皮肤/布/陶瓷/玻璃/植被/水/金属等；
- 注明喜欢的明暗/暖冷/材质部分，避免模型只学到颜色分布。

### 第 3 批（R18，首个正式入库批次）

- 20–30 张你有权保存和分析的线稿（可以包含第一批），导入器先做清洗/分类/人工复核；再扩至 30–50 张验证管道。
- 3–5 篇你有权处理的微信公众号或类似网页的 **URL 或 HTML+图片导出**；明确文章/图片保存与使用权限。无需验证码、Cookie、账号或绕过受限访问。
- 可选 3–5 份 Krita 工程、2–5 份真实绘制示范视频/轨迹。
- 标记每份许可：仅本地参考、允许上传具体模型、允许训练、允许公开展示。不同标志不能互相推断。

### 第 4 批（R19–R20）

- 优先复用全部历史失败作品、已获授权参考图、正式冻结的跨题材基准。
- 用户审查局部失败案例，并参与少量真实画质盲评；不要求持续提交大量新线稿。
- 另行隔离独立 held-out 任务。不能把 R20 封存基准混入训练、索引调参或 prompt 特例优化。

## 5. 最简素材交接表

本地 Agent 在受保护的 `private-references/` 素材目录下，以一份导入 manifest 管理源文件；未知信息可标 `unknown`，不得填“owned”来跳过许可核实。

| 字段 | 最低要求 |
| --- | --- |
| asset_id | 由导入器创建，不重复 |
| type | lineart / color_art / lineart_color_pair / kra / stroke_demo / article |
| path or URL | 本地相对路径或有权获取的原文 URL |
| creator/source | 作者或出处，不确定标 unknown |
| rights_basis | owned / public_domain / licensed / explicit_permission / unknown |
| local_use | yes / no / unknown |
| external_upload | yes / no / unknown，及授权的供应商或范围 |
| training | yes / no / unknown |
| publish | yes / no / unknown |
| tags | 主体、姿态、线条/色彩风格，自由补充 |
| comment | 喜欢/不喜欢什么、哪个部位要借鉴 |
| sha256 | 由工具在导入时自动计算，不能用户凭空填写 |

不要求用户手写完整 JSON 或哈希；只需传文件和简短说明，导入器应生成可审查的 manifest 候选，未填许可默认不能外发/训练/公开。

## 6. 减少本地反复验收的实际流程

- 每轮先离线验证和小规模云端原生测试（可用时），防止浪费 Windows/模型调用。
- R13 修复必须真实跨构建测试，因为这就是原生兼容问题；后续 R14 主要是离线几何/模型结构测试，R15–R17 适度本地真实画质 A/B，R18 本地图片清洗不需耗费大量 Krita native。
- R19 针对具体失败场景验证修订，不每次运行正式 24 题。
- R20 进行**集中、固定的 24 题正式验收**，全部失败计入分母。
- 对每类新画法建立“合成/小样→真实原生→可编辑画面→完整作品”的逐级门禁。失败立即记录，不刷更多笔数尝试撞过视觉评价。

## 7. 版本、命名与 PR 纪律

- 本规划放在独立 `docs/artist-roadmap-r13-r20` 分支，仅存目标文档、链接和开发规则；**不是** Round 13 功能分支。
- 每个 Round 创建并验证新的 `feat/roundN-topic` ref，分别 PR 到当前 main；禁止写到已有 R12 feat 分支/验收 docs 分支，也不直接 merge main。
- 同一轮内部可以有几个相关功能包；修复之前轮次的特定问题使用独立 fix 分支或已存在的合法同轮分支，不能污染其他轮次。
- GitHub Actions 必需检查按照仓库 Ruleset 执行；报告实际结果，不能用“预期通过”代替完成。
- 用户拥有 merge 和验收决定权；独立评审不足或有真实缺陷时保留为未通过。
- raw `artwork-results` 和 `private-references` 本地保存，不推送完整 KRA、用户私有图像或密钥到 GitHub。
- 如果开发中更新本规划，必须补充变更原因、影响、原标准、修改后的门禁，并遵守独立 docs 分支边界；不要静默重写 R12 失败报告。

## 8. 第一版基本完善之后的后续可选方向

**不把可选功能硬塞进 R13–R20 阻塞基础开发：**

- R21（若条件成熟）：专用视觉/线稿结构模型或真实笔触动作模仿学习。须先拥有明确合法训练许可、足量高质量标注/真实轨迹和独立测试集，并通过 A/B 证明超过简单检索。
- 更复杂的画风迁移、多参考精确约束、非常精细的人体/动物解剖与高分辨率画作、第三方专业资源兼容等，可分别立项。
- 用户如果只需要特定题材或风格，可在“可声明支持范围”的标准内优先打磨，但不能借此修改通用 24 项测试得分方式。
- 产品应保留人工可编辑和明确控制，允许“尚不能完成”的真实状态，不靠自我评价提高成功率。
